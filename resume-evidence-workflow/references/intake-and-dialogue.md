# Intake and Dialogue

Use this reference for `evidence` mode, a first substantial career experience,
transcript-heavy material, or any moment when an answer could open a new evidence
branch. The goal is a usable factual record, not a complete autobiography.

## Inventory before questioning

Inspect supplied material before asking the user to repeat it:

```text
resume and cover letter versions
portfolio, project pages, and public profiles
performance notes, project documents, and work samples
existing evidence bank and base resume
transcripts, voice notes, and rough outlines
target role, market, language, and job description
```

Record what is already known, what conflicts, and what is missing. A source file is
evidence of what the user previously presented; it is not automatically proof that
every line is accurate or current. Treat the latest explicit correction as
authoritative.

Choose the entry point from the material:

| Entry | Start with |
| :--- | :--- |
| Document-led | Extract the experience list, section order, dates, and role types, then confirm material facts. |
| Narrative-led | Identify experience boundaries and the main storyline before structuring details. |
| Portfolio-led | Separate project outputs from the user's contribution, relationship type, and outcome. |
| Voice-led | Preserve the account, detect likely transcription errors, and confirm high-risk fields. |

## Set a useful expectation

At the start of a substantial experience, give a non-binding estimate such as
`about five to eight core questions` and name the likely themes. State that one
complete answer can resolve several themes. Adjust the estimate as complexity
appears; do not turn it into a quota or promise.

Use the user's language. Introduce career frameworks only when they help the user
answer or when the user already uses them. Do not explain the full resume method
before hearing the work.

## Run three passes

### Recall

Establish the minimum causal story:

- what the work was and who it served;
- why it began and what was supposed to change;
- what the user personally did;
- what was produced;
- what happened afterward;
- which constraints or collaborators shaped the work.

### Lateral scan

Select only plausible branches from the radar below. A branch is plausible when it
fits the described work, not when it would make an impressive resume.

| Area | Look for | Natural prompt |
| :--- | :--- | :--- |
| Problem and objective | The need, audience, and reason the work mattered then | `What was happening that made this worth doing?` |
| Users and insight | Observation, interviews, support, segmentation, persuasion | `How did you learn what these people actually needed?` |
| Growth and adoption | Attention, participation, traffic, leads, repeated use | `Did anything change in how many people used or joined it?` |
| Retention and trust | Repeat participation, continuity, community health | `Did people come back, stay, or rely on it afterward?` |
| Commercial value | Advertising, sponsorship, pricing, sales, licensing | `Did money enter this in any form, even indirectly?` |
| Partnerships | Clients, creators, platforms, institutions, vendors | `Who outside the immediate team had to agree or participate?` |
| Content | Selection, creation, editing, packaging, distribution | `What did you decide to publish, change, or leave out?` |
| Product discovery | Need finding, assumption testing, alternatives, feedback | `What did you learn before deciding what to build or change?` |
| Data and decisions | Signals, datasets, patterns, evidence-led changes | `What number or observation changed a decision?` |
| Process and systems | SOPs, templates, databases, taxonomies, standards | `Did you leave behind a method other people could reuse?` |
| Delivery | Scope, sequence, resources, dependencies, scheduling | `What had to be coordinated for this to ship?` |
| Governance and risk | Complaints, moderation, privacy, compliance, safety | `What could have gone wrong, and who handled the edge cases?` |
| Ownership | Initiative, decisions, follow-through | `What did you notice or decide before someone assigned it?` |
| Judgment | Options, constraints, tradeoffs | `What else could you have done, and why did you choose this?` |
| Influence | Changing a decision without formal authority | `Whose decision changed because of something you said or showed?` |
| Learning | Failure, surprise, adaptation | `What did not work the first time?` |
| Leverage | Reuse, scale, automation, teaching, handoff | `Did the team use this again after the original task ended?` |

Ask only for the branches that could change a capability label, an evidence type, a
future resume selection, or the interpretation of ownership. Use the language of the
actual work rather than abstract resume vocabulary.

### Selective deepening

For a promising branch, establish the user's action, reasoning, constraint, direct
output, observed result, and boundary. Do not mechanically demand a metric or a
complete STAR field. Some valuable evidence is qualitative, incomplete, or negative.

## Question selection

Before each question, check whether the answer could:

- reveal a materially different capability or value branch;
- clarify the user's ownership or decision;
- resolve a conflict in dates, numbers, names, or status;
- change what should appear in a future resume;
- establish an event worth preserving for later use.

If none applies, defer the question. Search the current answer and existing records
first so the user is not asked to repeat known information.

Three practical question classes:

- **Discovery** opens a plausible branch and is most useful early.
- **Deepening** strengthens one branch with action, judgment, evidence, and outcome.
- **Administrative** resolves a fact needed for correctness or delivery.

Ask administrative questions only when they affect verification, interpretation, or
the current artifact. Exact meeting counts, exhaustive collaborator lists, and minor
tool selections rarely do.

## Cross-experience handling

When experiences share a workflow, audience, organization, or operating model,
establish the shared facts once and ask mainly about meaningful differences. Apply a
shared fact to another experience only when the user says it is shared. Use one
experience as a memory cue for another only when the context makes it plausible and
the answer could reveal useful evidence.

Do not automatically transfer a negative fact, a metric, or an ownership claim
between experiences that merely look similar. After two answers of `same as before`
or `already covered`, stop the mechanical scan and reassess the branch.

## Stop conditions

Stop or defer when:

- two successive answers add detail but no new signal;
- the branch repeats evidence already captured elsewhere;
- the user cannot retrieve the detail and precision is unnecessary;
- the branch is neither differentiating nor likely to affect later use;
- further questions would mainly satisfy completeness;
- user fatigue makes a checkpoint more valuable than another question.

Use a deferred list with a reason: `job-description-specific`, `low information
gain`, `needs source`, `user fatigue`, or `not currently retrievable`. Do not turn
it into an automatic questionnaire for the next conversation.

Completion means the meaningful experiences have been surfaced and scanned for
distinct value, not that every detail is recorded.

## Show the evidence preview

After a substantial answer, show only the neutral facts that would be added or
changed. Make the preview close to the bank entry: slightly professional, but not a
finished resume bullet. Include material uncertainty and ownership boundaries.

Good preview:

```text
The community account grew from 4,000 to 18,500 followers between March and
November 2025. You set the posting schedule and edited contributor drafts; two
other people handled visual assets. Sponsorship was explored but not signed.
```

Avoid labels such as `facts`, `capabilities`, or `provisional wording`. Do not append
an explanation of how the preview will become resume language. Ask implicitly for
correction by presenting it as the current update, not as a final decision.

## Event scan

After the main business facts are clear, make at most one short scan for a meaningful
problem, decision, disagreement, failure, constraint, or adaptation. Use one broad
natural question rather than walking through behavioral categories. If no event
emerges, stop. Preserve a compact event card in the bank; do not produce STAR answers
or an interview-preparation package.

## Voice and transcript input

Treat speech recognition as a fallible transport layer.

- Let the user speak at length, including nonlinear or colloquial accounts.
- Preserve qualifiers such as `大概`, `好像`, `我记得`, `可能`, and `没有`.
- Check names, titles, hierarchy, dates, durations, numbers, money, units, negation,
  ownership pronouns, and later corrections first.
- Mark a suspected recognition error instead of silently normalizing it.
- Offer one or two context-based alternatives and confirm at a compact checkpoint.
- Do not ask the user to reconfirm punctuation, filler removal, or harmless grammar.
- Never average conflicting dates or numbers.

If audio cannot be processed directly, request an automatic transcript or pasted
voice-to-text result and continue with the same correction protocol.

## Conflict types

Name the conflict before resolving it:

| Type | Response |
| :--- | :--- |
| Recognition conflict | Compare the likely word with context; ask once. |
| Memory uncertainty | Keep the uncertainty visible until the user confirms. |
| Source conflict | Show both sources and ask which is current. |
| Presentation choice | Keep the evidence fact and the chosen resume treatment separate. |

## Privacy and public examples

Never put a real user's identity or career facts into public documentation,
fixtures, screenshots, demonstrations, or examples. Use wholly fictional names,
organizations, dates, projects, and metrics. Changing only the name leaves the case
re-identifiable and is not sufficient.
