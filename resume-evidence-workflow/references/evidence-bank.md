# Evidence Bank

Use this reference whenever the evidence bank is created, expanded, corrected, or
used to support a resume claim. The bank is the durable factual source; a resume is
one presentation of selected evidence.

## Default form

Use a human-readable Markdown file unless the user requests another maintained
source. Markdown survives tools, stays portable between conversations, and is easy
to correct. After a meaningful milestone, offer HTML, Word, or another reading copy
only if the user needs it. Derived files must not become competing factual versions.

A common workspace is:

```text
经历库.md              factual bank and indexes
基础简历.md            current general resume content
简历版式档案.md        visual and structural defaults
基础简历.html          optional editable HTML master
项目素材库.md          optional selectable project angles
复用表达库.md          optional accepted presentations
```

The filenames may follow the user's existing organization. Preserve their current
names when they already have a usable workspace.

## Writing style

Write neutral, lightly edited facts that another person can reinterpret for a new
job description. Do not turn the bank into a resume draft.

- Preserve ordinary nouns and the real subject of each fact.
- Avoid keyword stuffing, promotional summaries, and compressed STAR bullets.
- Prefer `the newsletter grew to 18,500 subscribers` over `accumulated an
  18,500-subscriber user base`.
- Record scope and attribution even when the result is unimpressive.
- Keep possible resume use separate from the underlying fact.
- Preserve failed, partial, and cancelled work when it reveals judgment or learning.

Conversation feedback may use slightly more professional language. Copy that wording
into the factual record only when it preserves the neutral meaning; otherwise store
it separately as a possible later expression.

## Person-level index

Keep a compact index near the top of the bank:

- education and hard background facts;
- experience inventory;
- each experience's status: `unscanned`, `scanned`, `deepened`, or `deferred`;
- capability-to-evidence links;
- candidate story or key-event index;
- unresolved source and transcription conflicts;
- the latest confirmation date where staleness matters.

The index should support retrieval without duplicating the full experiences.

## Experience record

Use this shape when the corresponding information exists. Omit empty sections rather
than filling placeholders.

```markdown
## Experience name

### Basic information

### Overall background and objective

### What happened: Workstream or project A

#### Why it started

#### What the user did

#### What it directly produced

#### What happened afterward

### Results and data

### Responsibility boundaries and uncertain information

### Key events

### Reusable methods

### Capabilities currently visible
```

`Overall background and objective` explains why a collection of work existed. Each
major workstream then records its own trigger or problem. Do not repeat the same
background under every project.

### Identity

Record:

- organization or project name;
- team or organizational unit;
- official role and relationship type;
- location when relevant;
- precise dates and any broader presentation convention;
- source and latest confirmation date.

Relationship type is evidence, not decoration. Preserve employee, intern, part-time,
freelancer, contractor, volunteer, participant, creator, or project contributor
exactly. Do not upgrade an internship into employment through a section label.

### Context

Record the business or project background, users or stakeholders, the objective that
explains why the work existed, and known constraints. Distinguish:

- an objective the team explicitly stated at the time;
- the user's understanding at the time;
- the user's retrospective interpretation;
- an agent inference.

Only the first three may enter the factual bank with their proper attribution. An
agent inference stays a question or a clearly labeled uncertainty.

### Value branches

For each discovered branch, preserve:

```text
branch label and why it started
the user's own wording
personal and team actions
direct outputs
observed outcomes or failure
reasoning and tradeoffs
artifacts or links
capability signals
possible resume or interview uses
```

The branch label is a retrieval aid, not a claim that the user owned the whole area.
Use capabilities visible in the work rather than aspirational labels.

## Evidence chain

Use this lightweight chain internally:

```text
need or opportunity
  -> intended objective
    -> activities
      -> direct outputs
        -> observed outcomes
          -> continuation, reuse, or learning
```

Context, constraints, other contributors, and external factors may affect any link.

Distinguish:

| Layer | Meaning | Example |
| :--- | :--- | :--- |
| Activity | What someone did | Ran a contributor onboarding process. |
| Direct output | The immediate artifact | A guide, checklist, or trained cohort. |
| Outcome | What changed afterward | Fewer repeated review issues or faster publishing. |
| Continuation | Whether it persisted | Another editor used the process after the user left. |

An output is not an outcome. A contribution is not sole ownership. A later team
result is not automatically the user's personal result.

## Metrics and scope

Every number needs enough scope to remain honest:

- metric name and unit;
- personal, team, channel, account, or organization scope;
- period and `as of` date;
- source or confirmation;
- whether it is a snapshot, cumulative total, peak, or estimate;
- what the user actually influenced.

Never compute a growth rate from mismatched snapshots. Never present a team total as
personal output. Preserve an earlier value only when it explains chronology or growth.

Classify an update before editing:

| Update | Action |
| :--- | :--- |
| Correction | Replace the wrong value or fact; remove the obsolete error. |
| New snapshot | Keep the current value and date; retain older values only when useful. |
| Scope clarification | Correct the meaning everywhere the number appears. |
| Later development | Add the dated development and the user's actual relationship to it. |

## Key events

Preserve a compact event only when it contains meaningful tension, judgment, or
adaptation. Keep one to three strong events per substantial experience, not one per
behavioral category.

```markdown
#### Event name
- Situation and people involved:
- What became difficult or uncertain:
- The user's responsibility:
- What the user did:
- Why the user chose that approach:
- What happened:
- Whether the team or user later reviewed the work:
- Improvements identified or actually applied afterward:
- Useful question themes:
```

This is evidence enrichment, not an interview package. Do not generate STAR/CAR
answers or predict interview questions in this Skill.

## Reusable methods

Record a method only when the user actually applied it. Link the method to a real
project and preserve the decision or constraint that produced it. Do not insert
generic frameworks merely because they sound professional.

## Capability index

Capability labels must be recoverable from concrete evidence. A useful entry links:

```text
capability label
  -> experience and value branch
  -> strongest evidence
  -> ownership and scope
  -> unresolved limit
```

Avoid broad labels such as `operations`, `strategy`, or `leadership` when the evidence
supports only a narrower action. The index is a retrieval map, not a resume summary.

## Updating during tailoring

The bank remains writable during matching, rewriting, and review. When a new fact
appears:

1. search for the same fact, a synonym, or a broader entry that already contains it;
2. distinguish a new fact from a new phrasing of an existing fact;
3. show a short neutral update preview;
4. state whether it will be added, merged, or corrected;
5. allow the user to decline, identify duplication, or correct scope;
6. update the relevant experience and indexes promptly.

Do not require a formal approval exchange for every ordinary addition, but never hide
the write-back. If the user says not to store it, stop. If a duplicate is identified,
merge only genuinely equivalent records and preserve the more precise source.

## Evidence and presentation layers

- **Evidence layer:** what the user supplied or confirmed.
- **Presentation layer:** what the user chooses to show in a specific resume.

Keep the evidence layer unchanged when a resume uses a different presentation choice.
When the user explicitly requests a different date format, title presentation,
emphasis, compression, or omission, carry that instruction into the resume. If the
choice creates a material explanation risk, state the specific risk once, then
continue. Record the differing presentation separately when that prevents it from
overwriting the bank.

## Review the bank

Before using the bank for a high-stakes application, check:

- every metric has a scope and date;
- role and relationship types are clear;
- outputs, outcomes, and later developments are distinct;
- personal, team, and external contributions are separate;
- contradictions are resolved or visibly marked;
- the index points to real sections;
- no agent inference appears as a confirmed fact;
- private evidence has not leaked into examples or fixtures.
